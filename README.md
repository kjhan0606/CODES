# CODES

**Close-approach Orbit Dynamics and Ephemeris System**

CODES separates two scientifically different tasks.

1. `spk` downloads a time-continuous small-body SPK generated by NASA/JPL
   Horizons. This is the authoritative reproducibility product.
2. `propagate` runs a local sensitivity calculation. JPL DE440s supplies the
   Sun, planet, Earth, and Moon states. The local force model adds the solar
   Schwarzschild 1PN term, direct solar radiation pressure, Poynting-Robertson
   drag, solar-wind drag, and optional JPL-style `A1`, `A2`, and `A3`
   accelerations.

The default local backend is Fortran. It calls CSPICE at every force
evaluation, reads JPL `GM` values instead of multiplying separate `G` and
mass estimates, and uses `real(kind=16)` for the integrated state and force
sums. GNU Fortran reports 33 decimal digits on the current platform. The
SPICE input and output boundary remains IEEE-754 binary64 because that is the
precision of the JPL SPK interface.

## Important interpretation

The phrase "100th-order NASA integration coefficients" does not describe the
JPL data product accurately. Planetary and small-body SPK files store
piecewise Chebyshev coefficients whose degree is selected for each SPK segment.
The polynomial degree is not an orbit-integrator order and need not exceed
100. The Fortran backend uses an adaptive Dormand-Prince pair in real128
arithmetic. The optional SciPy backend uses eighth-order DOP853 in binary64.
Raising a formal integrator order to 100
would not remove uncertainty in the fitted initial orbit, close encounters,
small-body perturbers, Yarkovsky acceleration, or physical parameters.

A 100-year SPK is reproducible over its declared coverage. A 100-year nominal
trajectory is not equivalent to a 100-year impact prediction. Hazard work must
propagate the JPL covariance and compare virtual asteroids through close
encounters with a system such as JPL Sentry-II.

## Installation

From the project root:

```bash
python -m pip install -r neo_orbit_calculator/requirements.txt
```

## Authoritative 100-year SPK

```bash
python -m neo_orbit_calculator.cli spk 99942 \
  --start 2026-01-01 --stop 2126-01-01 \
  --output-dir neo_orbit_calculator/output
```

Horizons integrates the current JPL orbit solution with its registered force
model and returns a binary SPK. This mode needs network access when the SPK is
created.

## Horizons vector table

```bash
python -m neo_orbit_calculator.cli vectors 99942 \
  --start 2026-01-01 --stop 2126-01-01 --samples 101
```

## Custom force-model experiment

```bash
python -m neo_orbit_calculator.cli propagate 101955 \
  --start 2026-01-01 --stop 2036-01-01 --samples 401 \
  --a2=-1.9e-14
```

The compact 31 MB DE440s kernel is downloaded automatically. Its coverage is
1849 through 2150. Use a full DE440 or DE441 kernel when a wider interval is
required. The default force model also downloads the JPL SB441-N16 kernel and
includes all 16 of its most massive main-belt perturbers. Use
`--major-bodies-only` only for a reduced diagnostic run.

For a small artificial object, supply an area-to-mass ratio:

```bash
python -m neo_orbit_calculator.cli propagate 99942 \
  --start 2026-01-01 --stop 2036-01-01 \
  --area-mass 1e-5 --cr 1.2
```

Use `--backend scipy` for a binary64 cross-check. The default backend is
Fortran real128.

The solar-wind drag factor defaults to 0.35 times the
Poynting-Robertson drag term. This is a configurable secular approximation,
not a time-resolved heliospheric plasma model.

## Historical close-approach validation

From the project root:

```bash
python validate_neo_orbits.py
```

The regression run retrieves MPC ADES observation histories and official JPL
CNEOS close-approach records for ten NEOs. It initializes the local propagator
from the current Horizons state two days before each encounter, reproduces the
geocentric closest-approach epoch and distance, and compares heliocentric
osculating elements at a common epoch. Outputs are:

- `neo_orbit_validation_10cases.csv`
- `neo_orbit_validation_tables.tex`
- `appendixC_assets/neo_orbit_validation_10cases.png`
- `neo_orbit_validation_provenance.json`

This validates the force model and numerical propagation. It is not an
independent fit of a discovery-night orbit. Such a test also requires
topocentric observatory states, astrometric catalog debiasing, weighted
residuals, outlier rejection, a fitted covariance, and archived orbit
solutions that exclude later observations.

## Medium- and long-period comet modes

The apparition mode retrieves the JPL Horizons orbit associated with each
return and plots changes in return interval, semimajor axis, and perihelion
distance. The default `1P` configuration covers the historically identified
returns of Halley's comet.

```bash
python -m neo_orbit_calculator.cli comet-orbits 1P \
  --start-year 800 --stop-year 2000 \
  --output-dir neo_orbit_calculator/output/halley_orbits
```

For another comet, provide known return years when Horizons aliases do not
resolve them uniquely.

```bash
python -m neo_orbit_calculator.cli comet-orbits 12P \
  --return-years 1812 1884 1954 2024
```

The sky mode returns geocentric apparent coordinates, distances, and the IAU
constellation containing each requested position. It also writes a labeled
right-ascension and declination track.

```bash
python -m neo_orbit_calculator.cli comet-sky 1P \
  --epochs 2061-07-28 2061-08-15 2061-09-01 \
  --output-dir neo_orbit_calculator/output/halley_sky
```

Apparition records are separate fitted solutions. A modern comet solution
must not be extrapolated through ancient close encounters and then presented
as an observationally certified trajectory.

## Desktop interface

```bash
python -m neo_orbit_calculator
```

The integrated CODES window exposes NEO SPK retrieval, Horizons vectors,
local Fortran propagation, comet apparition histories, apparent
constellation positions, and the NEO and Halley validation suites. The
existing `neo_orbit_calculator` package remains the calculation backend.
`python -m neo_orbit_calculator.gui` is retained as an equivalent launch
command.
